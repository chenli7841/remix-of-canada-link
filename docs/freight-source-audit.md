# 运费来源与验收清单

本次规则：取消最低收费。量尺称重保存的运单费用是基础来源；员工在箱号、托盘选择合箱收费时，使用该容器自身运费替代内部基础运费。已经付款、已经确认的账单保留历史金额。

## 来源与显示

| 位置 | 计算或读取来源 | 本次处理 |
| --- | --- | --- |
| 量尺称重 | `scan.functions.ts` 的 `computeWaybillFeesCad`，调用 `measured-freight.ts` | 按线路、实重、尺寸及计费方式计算，保存到运单费用和重量快照；最低收费为零 |
| 订单费用 | `orders.functions.ts` 的运单汇总及数据库同步触发器 | 汇总保存的运单费用；合箱订单显示参考提示 |
| 箱号、托盘收费选择 | `ContainerBillingChoice.tsx`、`cartons.functions.ts` | 员工在容器选择 `split` 或 `merged`，不再读取客户收费偏好 |
| 合箱分摊 | `freight-allocation.ts`、`effective-freight.server.ts` | 合箱托盘优先于内部箱号，合箱箱号优先于内部运单；金额按分分配，汇总一致；读取全部兄弟运单后分摊 |
| 箱号、托盘列表及详情 | `cartons.functions.ts`、`container-chargeable.ts` | 费用按当前收费方式显示；内部运单收费重量读取保存快照，合箱箱号替代内部计费重量；缺失重量显示待核价 |
| 批次与客户费用抽屉 | `orders.functions.ts` 的 `computeBatchFeeSummary` | 运单费用或合箱分摊金额汇总；不再按客户总重量重新计算基础运费；未确认的过期快照重新汇总 |
| 前台及后台订单合箱提示 | `ConsolidatedFreightNotice`、`consolidated-freight.functions.ts` | 根据实际箱号、托盘收费方式显示“已合箱收费，订单费用只做参考” |
| 账单 | `invoices.functions.ts`、`duty.server.ts` | 实收运费使用有效分摊金额；普通运单的重量、单价明细使用保存快照，合箱分摊不会伪装成普通运单原价 |
| 自动微信量尺通知 | `wecom-freight-refresh.server.ts`、每日通知生成和发送入口 | 自动通知在生成、预览及发送前读取保存的运单运费；合箱金额标为参考。人工编辑内容和历史已发送内容保留 |
| 派送列表与明细 | `delivery-queue.functions.ts`、`delivery-summary.ts` | 明细读取统一分摊金额；额外费用只读明确设置值，不把基础运费当作额外费重复收取 |
| 对外客户查询接口 | `mcp/currency.ts` | 保存的费用汇总包含清关费，明确的零金额不会回退到旧金额 |
| 运费试算 | 线路设置和公开试算页面 | 取消最低收费；试算仅用于报价，实际订单以量尺结果为准 |

## 大批次完整性

- `fee-query.ts` 按稳定顺序分页读取全部费用来源。批次直挂、箱内及托盘内运单不依赖数据库默认单次返回数量。
- 合箱收费重量取箱号、托盘自己的线路规则，即使其线路与内部订单不同。
- 分页过程中发生读取错误时终止汇总，不返回部分金额。

## 历史数据与验证边界

- 已审查 8,004 张运单，修复 1,022 张符合条件的历史费用，8 个相关批次标记重新汇总。
- 修复前留有受权限保护的数据库备份；保护已付款、已确认账单及已关联账单的记录。
- 修复后审计：符合修复条件的差异为 0；523 张涉及已付款或已确认账单的差异保留原记录，未自动追收或退款。
- 自动检查覆盖取消最低收费、嵌套覆盖、分摊守恒、舍入、账单及付款快照保护、通知金额、收费重量、保险、附加费与超过单页数量的汇总。
- 未向真实客户发送测试消息，未执行实际扣款。后台与客户登录后的每一张页面未全部逐屏人工验收，不能把自动检查等同于全部人工操作验证。
